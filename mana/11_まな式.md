## 2. 全体像 — まな式の狙い

まな式は「AI（主にClaude Code / Claude / ChatGPT）とSNSを使って個人が収益化する」ための実践体系で、3つの層が相互に支え合う構造になっている。

1. **集客層（Threads / X / Instagram）**: 投稿を「集客・教育・販売」の役割に分け、痛みの言語化で読者の自己理解を変える発信を行う。フォロワー数よりリスト（公式LINE・オープンチャット）への登録を重視する。
2. **販売層（note / Brain / 講座・ローンチ）**: 商品は中身からではなくオファー（誰に・何を約束し・どう渡し・いくらで）から設計する。低単価noteで土台の売上を作り、相談・サポート・講座の高単価で積み上げる二段構え。販売前に教育コンテンツ3本と6つの教育（信頼・目的・問題・手段・投資・行動）を配信する。
3. **自動化層（Claude Code への委任）**: 投稿量産、教材・レター・販売ページ・特典スキル・VSL・予約投稿ツール・リサーチ・動画編集までを、AIエージェントに「決まりファイル（制約）＋材料ファイル（一次情報）＋依頼文」の3点セットで渡して実行させる。人間が担うのは材料の提供、角度の決定、判断、公開前の検品のみで、公開・送信・投稿自体は自動化しないのが原則。

この3層を束ねるのがルートの `SKILL.md`（まな式マネタイズAI）で、相談者の現在地を売上基準で3段階（0→1未達／1→10／月100万以上志向）に判定し、止まっている箇所を1つだけに絞って、数値で指定した次の一歩を返す相談AIとして設計されている。企画01〜08は、その自動化層を YouTube 実演動画＋特典PDF という形で切り売りした個別プロダクト群であり、CM動画スキルとAIまとめは動画・AIツール解説という別系統の派生教材である。

中核概念は次の4つに集約できる。
- **顧客視点への転換**: 投稿の主語を「自分」から「読者の悩み」に変える。投稿前に「読者は今何に悩むか／読むとどう変われるか／読み終えたら次に何をしてほしいか」の3問に答えられないものは出さない。
- **痛みの5層**: 出来事→感情→自己評価→恐れている未来→欲しい許可、まで掘ってから書く。
- **一次情報＝やってみた結果の差分**: 実績がなくても、失敗・試行の記録（何をした／何が起きた／数字・固有名詞／意外だった点）が投稿と商品の材料になる。
- **決まりファイルによるAI制御**: AIの暴走（数字の創作、約束表現、他者名の混入）を、プロンプトの工夫ではなく「読ませる制約ファイル＋書いてよい実績だけの台帳＋機械チェック」で抑える。

### 企画01_Threads運用 — Claude Code に任せる Threads 運用の土台ファイル

- **目的**: Claude Code に投稿を書かせる前に、毎回読ませる「決まり」と「実績」の2ファイルを整備し、AI生成投稿の品質と事実性を担保する。
- **仕組み・手順**:
  - ファイル1「投稿ルール（writing-rules.md）」: 冒頭に固定ルール6行を置き、人間が原稿を直すたびに、その修正理由を「足したルール」欄へ1行ずつ追記して育てる運用。固定ルールの内容は、1本100〜500字、疑問符・コロン・イコール記号を使わない、URLとハッシュタグを本文に入れない、根拠のない数字を書かない、1行目に製品名か数字を入れる、特定の煽り型の書き方をしない、というもの。
  - ファイル2「実績台帳（実績台帳.md）」: 投稿に書いてよい数字・体験だけを表形式（記号／書いてよい表現／出典／確認状況）で管理する。表にない数字・体験は書かせない、数字は台帳の値以下で書かせる、使わないと決めた行は消さず「使わない」と明記して残す、という運用。
  - 依頼時は「2ファイルを読んでから書いて」と1行添える。慣れた段階では Python のチェックスクリプトで台帳外の数字や禁止語を機械的に止める発展形も示される。
- **収益化の設計**: 本企画自体は YouTube 動画の視聴特典として配布される無料リードマグネットであり、直接の価格設計は資料内にない。仕組みとしては「運用の自動化ノウハウ」を無料で出し、後段の有料商品（企画03の自動販売機＝AIループ教材など）への信頼形成に使う位置づけ。

### 企画02改_note月100万 — 有料noteを1本出すまでの6ステップ

- **目的**: 自分の作業記録だけを材料に、売れている記事の「構造」だけを借りて、有料noteの無料部分と章立てを Claude Code に下書きさせる。
- **仕組み・手順（今日やること6つ）**:
  1. 目標額を価格帯別の必要販売人数に換算する表を作り、自分が書ける価格帯の1行だけ残して紙に貼る（低価格ほど必要人数が跳ね上がることを可視化し、高単価寄りに意思決定させる狙い）。
  2. 読者を1人に決める。推奨は「半年前の自分」。困っていたこと／調べたこと／手が止まった場所を10行程度で `読む人.md` に書く。思い出せない場合は AI に10問の聞き役をさせて引き出す。
  3. 自分の投稿・メモ・会話・管理画面の数字などの記録を1フォルダに集め、AIに「困っていたことと解決したこと」を日付・数字つきで10個抽出させ、「今の自分が乗り越え済みか」「同じ悩みの人をすぐ見つけられるか」の2基準で1つだけ残す。
  4. 売れている記事の無料部分を段落単位で分解し、役割と字数の表にする（実演例では14段構成、無料部分は全体の約7%）。文面は借りず、段の順番と役割という「箱」だけを借り、自分のネタを箱に流し込む。箱に入らない話は切る。
  5. 公開日を先にカレンダーで決めて出し、修正は公開後に行う。修正依頼は「直す箇所＋理由」を特定し、修正後に数字と類似度を再測定させる。
  6. 売れた後は購入者の感想・質問を1か所に集約し、AIに「無料部分で分かりにくい所を3つまで」「初見で分からない言葉の全抽出」をさせて無料部分を改修する。
- **プロンプト・設定の要点（決まり.md）**: 作業フォルダに置く制約ファイルの型として、記録にある数字・日付・出来事だけを使う／収入保証に聞こえる表現を使わない／使わない言葉を明記する／アカウント名・ハンドル・URLを書かない／お手本から借りるのは組み立てだけ／価格未定の段はプレースホルダで空ける／有料部分は章立てまでしか書かせない、の7項目が示される。実演では AI が原典との文単位の類似度を自ら測り、段階的に下げながら書き直した経過が記録されている。決まりの追加は「下書きで直した箇所を1行で追記する」「書かないことは否定文で1行1項目書く」という運用。
- **収益化の設計（仕組み）**: 価格帯別の必要人数換算、無料部分で信頼と納得を作り有料部分への境目を設計する構造、購入者の声による無料部分の継続改修、という販売の仕組み自体は手順として抽出できる。
- **収益化の設計（主張）**: タイトルがうたう「月100万」は目標設定の枠組みであり、本資料自体は達成を保証する記述を避け、むしろ決まりファイル側で保証表現を禁止している。実演記事の売上・ページビュー単価などの数値は講師側の実演記録として提示されたもので、第三者検証はない（第6章に分離記載）。

### 企画03_自動販売機 — AIループで商品販売一式を Claude Code に作らせる実演記録

- **目的**: X投稿を自動で回す仕組み（AIループ）を題材にした情報商材のローンチ一式（商品設計から販売ページ、特典、VSL、LINE文まで）を、Claude Code への指示だけで構築した過程を、指示文の原文と成果物の規模とともに開示する。
- **仕組み・手順（任せた仕事8つ）**:
  1. 商品設計: ローンチ構築スキルに商品案と特典案を渡すと、AIが中身・価格帯・位置づけ・リスト状況の4問を返し、回答から価格・限定人数・添削回数などの商品仕様を確定させる対話型設計。
  2. 教材作成: 大量の考察メモを壁打ち材料として渡し、章立て（稼ぐまでの話→稼ぎ方の全体像→組み方と運用→プラットフォームの仕組み解説）を生成させる。
  3. セールスレター: 2通構成で生成し、媒体（LINE・メール）用に記号を外した版も作る。途中で「手法は購入まで隠す」方針変更が入り全面書き直しになっている。最終的にレター配信自体を中止し導線を note に切り替えた経緯も記録されている。
  4. 販売ページ: 汎用フォームサービスで作った初版を破棄し、画像主体の縦長LPをホスティングサービスへ置く形に移行。画像24枚規模、文言の言い換え多数回。ベネフィット（どうなれるか）を前面に出し、機能的価値と手法の中身は隠す方針。
  5. 特典: 特典自体を「スキル」形式で4本（一次情報の種を出すスキル、AIツール紹介の投稿を作るスキル、プロンプト紹介の投稿を作るスキル、9本の投稿を返信でつなぐツリーを作るスキル）作らせる。種がない場合は書かずに止まる仕様をテスト用データで検証している。
  6. VSL: 15章構成の台本型を渡して章ごとに音声と画面を付けさせ、最後に連結して約54分の通し版にする。
  7. 動画視聴ページ: 視聴期限2日のカウントダウン付きページを作らせ、期限切れで動画が消えることまで動作確認する。
  8. LINE文: 2行の案を複数パターン出させ、トーンの指示（挨拶から入る、前提を語りすぎない、力作感を出す）で絞り込む。
- **もう1つの実演（10月21日版・自動販売機の依頼文と決まり）**: 作業記録から投稿21本（1日3本×7日分）を生成させる実演。重要な教訓として、21本を一括で頼むと AI が長時間何も書き出さず上限で停止した失敗が記録され、対策として (a)「1つ作ったらすぐファイルに保存して次へ進む」という進め方の1行を冒頭に足す、(b)依頼を種出し／前半の投稿生成／後半の投稿生成／予約表作成の4つに分割し、前の報告を受けてから次を渡す、という分割統治の手順が確立されている。作業記録の書式は「時刻・やったこと・意外だったこと・直し方」の4行1組で、「意外だったこと」が必須（無いとAIが聞き返してくる仕様）。決まりファイルは企画02と同型（記録にあることだけ使う、約束表現なし、反応誘導なし、他者名・URLなし、予約や投稿はせずファイル保存だけ）。
- **収益化の設計（仕組み）**: ローンチの構成部品（商品設計→教材→レター→LP→特典→VSL→期限付き視聴ページ→LINE告知）を AI への指示文の連鎖で量産する工程自体がノウハウの中核。特典をスキル形式にすることで「買った人がそのまま運用を再現できる」形にしている点、手法を購入まで伏せてベネフィットで売る LP 方針も設計として読み取れる。
- **収益化の設計（主張）**: 商品価格・限定人数・添削条件、X広告収益とされる金額、教材やレターの字数・制作期間などは講師側の提示値であり、検証手段は資料内にない。第6章に分離する。

### 企画04_リサーチツール — 伸びた投稿の収集・分析・配信の仕組みを Codex に作らせる

- **目的**: 複数SNSで伸びている投稿を定期収集し、定型で分析して、Discord と閲覧サイトに届けるリサーチ基盤を AI コーディングエージェントに構築させる。
- **仕組み・手順**:
  - 依頼文の骨格: 対象媒体（X・Threads・Instagram・TikTok・YouTube から使うものだけ残す）、取得手段は公式APIを優先し、公式APIで他者の投稿が取れない媒体は先に経路・費用・取得可能指標を報告させる、依頼受付チャンネルと配信チャンネルを分けた Discord 運用、依頼をスプレッドシートに蓄積し週1回決まった曜日にまとめて調査するバッチ方式、結果は公開ページと管理者ページを分けたサイトで閲覧可能にする。
  - 採用条件はパラメータ化されている: 投稿からの経過時間の上限、媒体ごとの表示・再生数と いいね 数の下限、フォロワー数の下限、1依頼あたりの採用件数、月額費用の上限。数値条件の判定と重複判定はプログラム側で先に行い、条件を満たしたものだけを詳細分析に回す二段構え。
  - 停止条件: 規約同意・ログイン・人間確認・権限付与・キー保存・課金が発生する操作の手前では必ず止めて人間に確認させる。
- **分析14項目（1件ごとの定型）**: 冒頭の引きつけ方、内容の構成順、伸びた理由の仮説（末尾に因果は未検証と明記）、自分の投稿で試せる手順と「言い切ってはいけないこと」、確認範囲と限界（何を照合し何を未確認としたか）、狙う相手と悩み、ネタの切り口、投稿の型を1行で表したもの、空欄穴埋め式の台本、自分の話に差し替える箇所、架空の構成練習例であることを明示した自作例、撮影・執筆手順、投稿前チェック、分析工程の記録。借りるのは型だけで、元の投稿の文・人物・実績は借りないのが原則。

### 企画06_操作画面切り出し — 画面収録と個人情報マスキングの制作手順

- **目的**: AIツールの操作画面を動画素材として安全に切り出す。個人情報やアカウント情報が映り込まない収録・加工・検証の工程を定型化する。
- **頼み方の文（1文の型）**: 「何を／どの窓だけ録るか／何を消すか／どこに重ねる形にするか」の4要素を1文にまとめ、最後に文字認識（OCR）で氏名が0件か確認させる一文を付ける。対象は専用ウィンドウやアプリの窓だけに限定し、画面全体は録らない。尺や細かい位置は初回は決めず、出てきた物を見て1つずつ直す進め方。事例として、チャット画面の収録、公式ヘルプの必要段落だけを出典付きの透明PNG札にする切り抜き、アプリ窓へのクリック位置の輪描き、場面ごとの差し込み札の一括生成、が挙がる。
- **録る前のチェック表の要点**: 映さない物の一覧（氏名・メール・アカウント・会話一覧・フォルダパス・他者の氏名）を最初に1回AIへ渡して恒常ルール化する。ウィンドウサイズを用途別に固定する、高解像度で撮り必要なら分割撮影してつなぐ、録画上限時間は作業見込みより長めに取る、無操作時間が一定続いてから録画開始する、クリック位置と時刻を同時記録する、ウィンドウを閉じる前に録画を止める。ブラウザ収録時はサイドバーを閉じ、アカウント名欄や利用上限表示、氏名が出る見出しを隠し、クッキーバナーは文言が完全一致する拒否ボタンだけ押す。
- **撮った後の処理**: フレームレートを30fpsに統一する（可変フレームの収録を補正）、ウィンドウが一瞬小さくなる・黒くなるコマを除去する、クリック位置の輪は画面変化の少し前の時刻に置く、全コマをOCRで読み、ぼかしは該当する四角い範囲だけ・画面が動き出す前で区間を切る、否定語や数字を含む文は行の両端が入る大きさまでしか寄せない（文意の誤読防止）。
- **動画に置く前**: 札の見出しは画面の外の白帯に置く（重ねると下の行が隠れる）、拡大の基準は左上に取る（中央基準だと左端の番号や文頭が切れる）、縦型リールの下部約500pxには字を置かない（タイトルやボタンと重なる）、4K書き出し時は札も4K解像度で作る、完成動画を再度OCRで読み出してはいけない言葉が0件であることを確認する。

## 4. CM動画スキル（code-cinema）— パイプラインと仕組みの要約

動画生成AIを使わず、HTML／GSAP／Three.js 等のコードで全編の動きを著作してショートCMを完成させるスキル一式。

### パイプライン

1. **ヒアリング（intake）**: 既存の会話・添付・既存プロジェクトの BRIEF から埋められる項目は聞き直さず、未回答分だけを最大3項目にまとめて聞く。必須は「テーマ（何を・誰に・何を伝えるか）」と「画像生成方針（GPT Image 2 を使うか）」。画像方針は制作ごとに確定し、過去作品での許可を新規依頼に自動適用しない。「演出はおまかせ」は画像方針の回答とはみなさず、「案を見て決める」は未確定（undecided）として扱い、生成を含む作業は方針確定まで止める。提供ロゴの使用と画像生成の可否は別軸として区別する。
2. **演出案（directions）**: 原則3案。各案にタイトル、映像化の方法、主役・質感・カメラ・全編の動き、配色と文字、音の方向、画像生成の要否を含め、説明だけで場面が浮かぶ粒度で出す。発想の引き出しとして10系統（立体彫刻型、文字パフォーマンス型、紙芝居型、物理遊び型、建築フライト型、光学フィールド型、編集印刷型、図解型、素材研究型、写真シネマ型）が用意されているが、固定テンプレートではなく起点と位置づけられる。別案の条件は、主役・構図・カメラ・展開のうち2つ以上、全体で3軸以上を変えること。色替えだけは別案に数えない。
3. **制作データ化**: プロジェクトごとに BRIEF.md（テーマ、正確な表示文言、対象、用途、尺、アスペクト、画像方針、使用可能素材、選択案、音の方針、本数）、design.md、STORYBOARD.md、directions.json を作る。画像方針は allowed / forbidden / undecided の3値で記録し、映像ソースも code-only / provided-assets / mixed で記録する。通常は汎用ビデオ制作の自動フローに引き継ぎ、二重のヒアリングをしない。
4. **制作（production）**: HyperFrames を土台に、Three.js 0.181.2／GSAP 3.14.2 相当の固定バージョンで制作する。レンダーの決まりとして、固定寸法と正確な尺をルートに持つこと、GSAPタイムラインは一時停止状態のものを同期的に1つだけ登録すること、WebGL描画はフレーム時刻から決定的に計算し前フレームへの加算や現在時刻・無制限ループを使わないこと、シーク時はコールバック抑制付きで描画関数を明示的に呼ぶこと、が定められている。画像なしで奥行きが要る場合は、厚み・曲率・閉じた端面・法線・影・視差で作り、平面画像の拡大を3Dと呼ばない。生成画像を使う場合も、長い静止画ズーム主体の構成を避け、写真に任せる場面とコードで動かす場面を分けて設計する。音はBPMと主要カットと静けさの位置を先に決め、波形合成で作る場合も全テーマ同一曲にしない。音量の目安は概ね −16〜−18 LUFS、トゥルーピーク −1.5 dBTP 以下（用途指定が優先）。
5. **検証と納品**: フレームワークのチェック、最初・最後・各境界・最も密な場面の目視、時刻を往復させた再描画の一致確認を行い、最終レンダー後に finalize スクリプトで実MP4を検査して納品する。完成MP4、マスター、編集用ソース、視聴用ページ（watch.html のテンプレートにタイトル・動画・ポスターのパスを差し込んだもの）を渡す。ソースからは絶対パス・キャッシュ・認証情報を除く。
6. **履歴（design_history）**: 完成後に directions.json の要約（系統、主役、素材、レイアウト、カメラ、遷移、タイポグラフィ、配色、画像方針、評価）だけを履歴に記録し、次回企画前に直近分を参照して反復を避ける。完全なプロンプトや顧客情報は保存しない。評価は明示された場合だけ accepted / rejected とし、通常は unrated。

### 主要スクリプトの構造

- `scripts/finalize_video.py`: FFmpeg / ffprobe のみでマスターMP4を検証し納品物を生成する。引数で期待する幅・高さ・fps・尺・音声の要否・出力先・プレビュー幅などを受け取り、解像度・フレームレート・尺・フレーム総数の一致、全編デコードの無事、音声のラウドネス測定（loudnorm）とトゥルーピーク警告を確認する。その上で視聴用コピー（縮小エンコード）、実フレームからのポスター画像、複数時刻のフレームを並べたコンタクトシートを生成する。ファイル名は安全な英数字パターンに制限する。
- `scripts/design_history.py`: 演出の指紋だけをローカルJSONに保存する。必須フィールドと値の長さ、画像方針が確定済みであること、評価の3値を検証し、ファイルロックと一時ファイル経由の原子的置換で最大50件を保持する。サブコマンドは recent（一覧）、compare（過去作との共通軸の抽出。4軸以上一致で反復レビューを促す。あくまで完全一致の機械比較であり意味的類似の保証ではないと明記）、record（登録、同プロジェクトは置換）。
- `assets/runtime/three-stage.mjs`: 照明と決定的描画の補助。WebGLレンダラー（アンチエイリアス、描画バッファ保持、高性能GPU優先）、sRGB出力、ACESトーンマッピング、PCFソフトシャドウ、RoomEnvironment を基にした環境反射、キーライト（影付き平行光）・リムライト・環境光を備えたステージを生成する createStage 関数を提供する。主役と動きは含まず、作品ごとに著作する前提。
- `assets/`: フォント4種（Instrument Serif、Manrope、Noto Sans JP、Zen Kaku Gothic New）とそのライセンス、Three.js / GSAP / RoomEnvironment のベンダーライブラリ、視聴ページのテンプレート watch.html が同梱される。プロジェクトへは使う資産と対応ライセンスだけをコピーする決まり。
- `references/lessons.md`: 実制作（銀色立体のCMシリーズ）からの教訓集。「同じ雰囲気」を同じ形の再利用と解釈しない、複数案では主役と展開を変える、画像なしの選択に写真素材や静止画ズームを黙って持ち込まない、立体と言うなら視点変化で面の見え方と隠れ方が変わる画にする、一度通ったプレビューだけで納品しない、4Kの主張は実解像度に合わせる、等。末尾にスキル改訂時の分岐確認シナリオ表（10ケース）がある。

### 収益化の設計

スキル自体に価格や販売導線の記述はない。位置づけは制作ワークフローの教材・特典としての配布物であり、CM制作サービスや教材販売の制作基盤として使う想定と読める（この点は推測ではなく、ファイル内に販売設計が存在しないという未確認事項として第6章にも記す）。
